# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

A personal film-log site (cinema.shubhambhatia.in) built from a Letterboxd diary CSV export.
There's no database and no runtime API calls: `data/diary.csv` (and optionally `data/reviews.csv`)
is read at build time, enriched with TMDB data, and everything — the log, every film's own page,
stats, and collections — is statically generated by Next.js.

## Commands

```bash
npm run dev     # dev server
npm run build   # production build — statically generates every film page (real TMDB calls if TMDB_API_KEY is set)
npm run start   # serve the production build
npm run lint    # next lint
```

There is no test runner configured. Ad-hoc verification during development has been done by
running small scripts with `npx tsx` that import directly from `lib/*.ts` (e.g. mocking `fetch`
to unit-test `lib/tmdb.ts` functions, or calling `lib/movies.ts` against the real `data/diary.csv`
without a TMDB key to confirm graceful null/empty fallback).

`TMDB_API_KEY` (v3 "API Key", not the v4 Read Access Token) is optional — copy `.env.example` to
`.env.local`. Without it, every `lib/tmdb.ts` fetch function returns null/empty and the UI falls
back to a plain text-only design.

## Architecture

**Data flow:** `lib/letterboxd.ts` → `lib/movies.ts` → pages. Each layer only adds what it needs:

- `lib/letterboxd.ts` — `loadDiary()`/`loadReviews()` parse the CSVs into `DiaryEntry[]` /
  `Map<reviewKey, text>`. `findCsv()` recursively searches `data/` (depth ≤ 3) for a file named
  exactly `diary.csv` or `reviews.csv`, so a user can drop a whole unzipped Letterboxd export
  folder into `data/` without hunting for individual files. A diary entry's `slug` is
  `slugify(name)-year-watchedDate`, used as the film detail page's route param.
- `lib/tmdb.ts` — one function per TMDB endpoint needed, each independently graceful (returns
  null/empty if `TMDB_API_KEY` is unset or the fetch fails), each cached via Next's `fetch` data
  cache (`next: { revalidate: THIRTY_DAYS }`, deduped across the build by identical URL).
  `fetchTmdbEnrichment` (search + credits, 2 calls) covers what the grid needs; trailer,
  collection membership, and recommendations are separate calls only made on the pages that need
  them, to avoid paying for them on every card.
- `lib/movies.ts` — `getMovies()` enriches the whole diary (fanned out via `mapWithConcurrency`,
  limit 8, to bound parallel TMDB calls); `getMovieDetail(slug)` adds the one film's trailer and
  recommendations, and cross-references recommended TMDB IDs against `getMovies()`'s own IDs to
  mark ones already in the log as "Watched" and link to their own page instead of out to TMDB.
- `lib/collections.ts` — groups the enriched movies by TMDB `belongs_to_collection`, drops
  single-film or zero-watched collections, and sorts completed-before-in-progress.
- `lib/stats.ts` — pure functions over `DiaryEntry[]` only, no TMDB dependency.

**Pages** (`app/`): `/` (grid + search + 4★ filter + genre chips), `/film/[slug]`
(`generateStaticParams` from `getAllSlugs()`), `/stats`, `/collections`. All statically generated
— visiting the site costs nothing at runtime; all TMDB cost is paid once at build time.

**Privacy boundary:** `.gitignore` ignores `data/**` except `diary.csv`/`reviews.csv` anywhere
under it — the rest of a Letterboxd export (`ratings.csv`, `watched.csv`, `watchlist.csv`,
`comments.csv`, `likes/`, `profile.csv`) is treated as more private than "movies I've watched" and
must never be committed. Don't loosen this without the user explicitly asking.

## Workflow

All changes — including data updates (a new `diary.csv`) — land on `main` via pull request, never
a direct push. See `ROADMAP.md` for what's shipped and the reasoning behind each phase.
